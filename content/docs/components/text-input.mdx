## When to use

Use a text input for short answers people type:

- **Names**, like a given name or surname.
- **Contact details**, like an email address or mobile number.
- **Reference numbers**, like a PhilSys Card Number.

Use something else when:

- **The answer is a date.** Use a [Date input](/docs/components/date-input), which splits it into day, month and year.
- **People choose from a fixed list.** Use a [Radio group](/docs/components/radio-group) or a [Select](/docs/components/select), so they can't type an answer you don't accept.
- **The answer is several sentences.** Use a textarea, so people can see everything they've written.

## Usage

```tsx
import {
  Field,
  FieldDescription,
  FieldError,
  FieldLabel,
} from "@/components/ui/field";
import { Input } from "@/components/ui/input";

<Field>
  <FieldLabel required>Given name</FieldLabel>
  <Input required autoComplete="given-name" />
  <FieldDescription>Write it as it appears on your birth certificate.</FieldDescription>
  <FieldError match="valueMissing">Enter your given name.</FieldError>
</Field>;
```

## Examples

### Validation

Check answers when people submit the form, not while they type. Use Base UI's `Form`: it checks every field, then moves focus to the first one with a problem. Add one `FieldError` for each problem, with `match` set to the check that failed.

<ComponentPreview name="text-input-validation" />

### Errors from your server

When your own code finds the problem, set `invalid` on the field and `match` on the error. Without `match`, the error only shows for the browser's own checks.

Inside Base UI's `Form`, clear `invalid` once people change the answer. The form won't submit while a field is marked invalid.

## Content guidelines

- **Labels** say what to enter: "Given name", not "Name 1".
- **Placeholders** show an example ("For example, Juan"). Don't put instructions in a placeholder: they disappear when people start typing.
- **Required fields:** mark them with `FieldLabel required` and the `required` attribute, and say "\* means required" once near the top of the form. If most fields are required, mark the optional ones "(optional)" instead.
- **Error messages** say what's wrong and how to fix it: "Enter your email address in the right format, like juan@example.com", not "Invalid input".

## Props

The label, hint and error are [Field](/docs/components/field#props) parts. See their props there.

`Input` accepts every prop of the HTML `<input>` element, like `type`, `autoComplete`, `inputMode` and `required`.

## Accessibility

### What Habi handles

- **Labels:** `FieldLabel` is linked to the input, so clicking the label focuses the input and screen readers read it.
- **Descriptions and errors** are linked to the input with `aria-describedby`, so screen readers read them when the input gets focus.
- **Errors aren't just red:** each one has an icon and text.
- **Text size:** inputs use 16px text, so phones don't zoom in when people tap them.
- **Focus:** a 2px blue outline shows which field is active, even on a field with an error.

### What you need to do

- **Give every input a visible `FieldLabel`.** A placeholder isn't a label.
- **Set `autoComplete`** on fields about the person, like `given-name`, `email` or `tel`, so browsers can fill them in (WCAG 1.3.5).
- **Pick the right keypad** for phones: `type="email"` for email addresses, `type="tel"` for mobile numbers, and `inputMode="numeric"` for reference numbers like a PhilSys Card Number. Don't use `type="number"` for numbers people don't count, like IDs, because it can round long numbers and changes the value when people scroll.
- **Use Base UI's `Form`**, or your own submit handling, to move focus to the first field with an error after people submit.
